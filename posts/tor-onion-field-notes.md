给 Tor 接上代理，最容易检查的是“网页能不能打开”。但一个能打开的网页，回答不了我真正想确认的几个问题：它是不是经过了 Tor？代理断掉以后，会不会偷偷换一条路？设置里写着 Ahmia，为什么眼前的搜索框还是 DuckDuckGo？

这篇写的是 2026 年 11 月 14 日那次配置与浏览器实测。它不是一份到处都适用的匿名上网配方，而是把一套具体环境拆开看：哪些地方接通了，怎样确认的，还有哪里没解决。

文中的图帮助解释路径；真正的结果仍然以当时的运行记录和页面证据为准。本文由 AI 辅助整理，概念插画是生成图，不把它们当作实验截图。

# 先确定要去哪里，再讨论怎样过去

![深网、暗网与公开网页的概念图：深网包含私人邮箱和登录系统；暗网只是特殊网络中的部分内容；示意不按规模比例绘制。](assets/images/posts/tor/web-layers.svg)

这次要验证的是 Tor 和几个公开的洋葱服务首页，不是搜集一份“神秘网站大全”。先把几个容易混在一起的词拆开，后面的测试才不会变成自说自话。

私人邮箱、登录后的云盘和内部数据库不能被搜索引擎直接索引，也属于通常所说的 **deep web**，并没有因此变成暗网。**dark web** 强调通过特定网络或软件访问；Tor 的 `.onion` 是一种例子。

Tor Browser 还能打开普通 HTTPS 网站。所以，“我用 Tor 打开了一个页面”和“我打开了一个洋葱服务”不是同一项结果。后面有一个只打开了公网首页的观察，我没有把它算进洋葱站点的通过名单。

# 网页打开了，究竟是谁看见了请求？

![普通 HTTPS 网站的典型 Tor 电路：浏览器经入口守卫、中继和出口到达网站。各节点掌握的信息不同，HTTPS 另在应用层保护传输内容。](assets/images/posts/tor/onion-routing.svg)

要判断有没有“走对路”，至少得知道这条路长什么样。

访问普通网站时，典型 Tor 电路经过入口守卫、中继和出口。不同跳处理不同层的保护，通常单个中继不会同时掌握通信的真实来源与最终目标。图里画的是这种常规路径，不是所有攻击情形的安全证明。

**直接连入口时，入口知道连接来源；出口知道访问目标。** 如果目标网站没有 HTTPS，出口到网站之间的内容还可能暴露。HTTPS 是另一层保护，不能因为用了 Tor 就省掉。

我在这里关心的不是“是不是多套了一层”，而是那一层改变了谁能看见什么。只有先分清这些角色，才有办法讨论后面加进去的 Clash。

# 洋葱服务没有那个普通出口

![概念插画：访问者与服务端各自穿过柔和的玻璃环，在中央会合。此图只表达会合的意象，不表示协议节点数量。](assets/images/posts/tor/rendezvous-art.webp)

![洋葱服务简化协议图：先通过服务描述符和介绍点建立联系，访问者与服务端各自建立电路，在会合点交换数据，不经过普通出口节点。](assets/images/posts/tor/onion-rendezvous.svg)

如果访问的是 `.onion`，前一张图就不能直接照搬。

客户端先读取服务描述符，经介绍点传递会合信息；随后客户端和服务端分别建立电路，在 **rendezvous point（会合点）** 连接起来。介绍点负责前面的联系，会合点负责后面的连接，它们不是同一个角色。

这个过程不需要先从普通 Tor 出口回到公网，再寻找一台“藏起来的服务器”。所以，讨论洋葱服务时，我不能再用“把出口也套进本机代理”这种说法。

上面的玻璃环是会合的视觉比喻，下面的线路图才负责说明流程；都没有把省略掉的密钥协商细节冒充成完整协议。

# Clash 要接在 Tor 前面，不是替换浏览器代理

![本次实验的连接链：浏览器保留本地 Tor 代理，本地 Tor 经受限转发连接 Clash，再经过加密代理节点进入 Tor；网站仍看到 Tor 出口。](assets/images/posts/tor/clash-chain.svg)

这次采用的顺序是：**浏览器 → 本地 Tor → Clash 的专用代理通道 → 远端代理节点 → Tor 网络**。访问普通网站时，后面再接 Tor 出口与网站；访问洋葱服务时，则走前面说的会合流程。

这里有一个很容易配错的位置：我没有把浏览器的网页代理直接换成 Clash。那样虽然也可能打开普通网页，却可能把 Tor 整段绕过去。

另一个要检查的是规则。Clash 是代理和规则处理工具，不等于某一种 VPN 协议；填入本机代理端口，也不能证明请求一定去了远端代理节点，规则里可能还有 `DIRECT`。这次为 Tor 单独建立了不含直连选项的通道。

这样改动的是进入 Tor 之前的一段：入口看到的来源可以变成代理节点，但代理服务方仍可能知道用户的连接来源。信任没有消失，只是换了位置；多一跳也不保证更快。

这不是我推荐所有人照抄的固定组合。[Tor 官方关于 VPN 的说明](https://support.torproject.org/tor-browser/general/vpn-with-tor/)同样提醒，应先理解自己的威胁模型，再决定是否组合使用。

# 我更想知道的是：断掉以后会怎样？

![概念插画：一条细光线穿过玻璃桥上的门，旁边的门保持关闭。表达代理失效就停止，而不是寻找不安全捷径。](assets/images/posts/tor/gate-art.webp)

连通时的路径检查，只完成了一半。真正容易被忽略的是错误处理：指定代理不可用以后，程序是停下来，还是换成直连继续工作？

这次采用的是 **fail closed：失败就停止**。在指定启动方式下，浏览器和 Tor 位于仅有回环接口、没有外网路由的网络命名空间里，只留下通往专用 Clash 通道的受限转发。

当时的直接 IPv4、IPv6 和 DNS/UDP 探测都被拒绝，代理失效模拟也没有回退直连。这些观察支持的是：**这套启动路径有降低误配置直连风险的约束**。

它没有覆盖其他应用，也没有覆盖绕过这个启动方式打开的程序。下载文件若交给外部阅读器，已经是另一个边界；软件或配置更新之后，也需要重新检查。几项探测通过，不能变成“这台电脑从此绝不泄漏”的保证。

这张门的插画想表达的只有一件事：既然要求不走别的路，出错时就不该悄悄把另一扇门打开。

# 五个站点都打开了，但等待不能混着算

![本次实际 Tor Browser 页面截图拼图：Riseup、Tor Metrics、Ahmia、Tor Project 与 SecureDrop 均显示正常正文并返回 HTTP 200。截图不是生成插画。](assets/images/posts/tor/five-sites-evidence.webp)

![五站首次验收耗时图：Riseup约13秒，Tor Metrics约17秒，Ahmia首页约28秒；Tor Project和SecureDrop首次超过45秒后续复测通过。复测缓存时间不能当作首次速度。](assets/images/posts/tor/observed-times.svg)

路径检查之后，才轮到网页本身。不能看到 SOCKS 握手就宣布“网站正常”；这次在安装的 Tor Browser 里实际打开页面，核对正文、页面状态、HTTP 200 和截图。

最终确认的五个洋葱服务是 **Riseup、Tor Metrics、Ahmia、Tor Project 和 SecureDrop**。地址来自相应公开官网或 `Onion-Location`，没有靠猜同名镜像凑数。

首次验收记录里，Riseup 约 **13 秒**，Tor Metrics 约 **17 秒**，Ahmia 首页约 **28 秒**。Tor Project 和 SecureDrop 则先超过了 **45 秒**，之后复测才显示正常正文。

后两者还有热缓存下的 **0.37 秒和 3.52 秒**。这些数字如果只挑最漂亮的摆出来，很像一次巨大的提速；但它们不能和前面的首次打开公平比较。代理测速、Tor 建路和网页检查也不是同一种计时。

因此，我只把它们当作一次环境中的单次观察，不当作 Tor 的统计基准，更不许诺这些站点会一直在线。

失败的部分也留着：ZeroBin 的公网首页能经 Tor 打开，但它公布的 v3 onion 地址返回了**服务描述符未找到**。Sci-Hub 只验证了公网首页，没有检索或下载资料，因此不算洋葱服务通过。其他没能核实当前地址的名称，也不写进成功名单。

# “为什么还是 DuckDuckGo？”这个反馈没有错

![两个搜索框的区别：地址栏默认引擎已经是Ahmia，但该版本Tor内置主页仍单独使用DuckDuckGo；另有Ahmia查询返回首页的未解决问题。](assets/images/posts/tor/two-search-boxes.svg)

这次最值得留下的一段排错，是一个看起来很小的界面问题：默认搜索引擎已经改成 Ahmia，眼前怎么还是 DuckDuckGo？

问题出在“默认搜索引擎”不负责我看到的所有搜索框。该版本 Tor 的内置欢迎页有独立实现，不跟随地址栏的引擎设置。只读配置文件，会以为已经改完；真正打开页面，才会发现用户反馈说的是另一个入口。

后来从运行中的浏览器内部确认，普通和隐私搜索引擎都已是 **Ahmia**，再把主页改为 Ahmia，新标签页改为空白，避开那个独立的欢迎页搜索框。界面和网页语言偏好统一为 **English (US)**，没有用堆扩展的方式改造浏览器。

但这不是一个可以写成“全部解决”的结尾。

Ahmia 的测试查询和正常表单提交都回到了首页，没有验证到正常搜索结果。我没有足够证据断定原因一定在本机或站点端。最后能留下的结论只有：**引擎设置已生效，搜索功能未完全验收。**

能打开首页，不等于能用它搜索。把这个未完成状态写下来，比再截一张首页然后宣布成功更有用。

# 配置记录的价值，不是一句“绝对匿名”

![隐私边界图：代理失效应该停止；隔离仅覆盖指定启动方式；真实身份登录、漏洞、恶意软件与流量关联仍需考虑，不能许诺绝对匿名。](assets/images/posts/tor/privacy-boundaries.svg)

回头看，这次配置其实包含好几件不同的事：把 Tor 接到指定代理、限制失败时的退路、核实洋葱地址、等待真实页面，再处理浏览器界面与设置不一致的问题。

把它们统称为“配置成功”太粗了。下一次出问题时，我更需要知道的是：哪一段测过，测试看到的是什么，哪些结论并没有被证明。

English (US) 和保留标准抗指纹配置，可以朝减少与常见用户差异的方向走，但并不是单独的匿名保证。真实身份登录、外部程序打开文件、浏览器漏洞、恶意软件和流量关联，仍然需要另外考虑。

所以这篇不是教人通过“多套几层”获得隐身能力。它更像给以后排错的自己留的一张路线图：这里接通了；这里断开后确实停了；这里还卡着，别把它忘掉。

# 资料、方法与这次修订

- **时间**：配置与浏览器验收发生于 2026-11-14，文章初次发布于 2026-11-15，2026-11-17 按个人技术手记的方式重新组织叙事。此次修订没有重跑 Tor 测试，不把旧记录说成今天的网络状态。
- **范围**：只验证公开首页，不登录、不提交匿名文件、不创建粘贴、不下载论文或书籍。加载耗时是单次验收记录，缓存复测另记。
- **AI 与图像**：本文为 AI 辅助学习记录。封面、会合场景和门的意象由 `gpt-image-2.6` 原创生成，不是拓扑或实验凭证；线路与数据图为独立制作的 SVG，不展示个人 IP、本机端口和代理节点信息。
- **真实截图**：五站拼图来自当时的浏览器页面，不含账号、书签、地址栏和个人网络信息。各站页面内容、标志与设计归相应权利人，仅作有限技术说明。
- **测试收尾**：当时测试结束后关闭临时控制服务、恢复临时推荐设置，保留正常窗口与原有抗指纹、本地 DNS 禁用、WebRTC 禁用和不回退直连设置。这不是完整安全审计。
