迁移到 Linux 是否成功，不该只看能不能启动桌面。对我来说，更有用的验收题是：拿到一份课件，能不能读；写完一段代码，能不能编译、测试、调试；最后交出去的文档，别人能不能正常打开。

这篇记录的是我从 Windows 转向 Linux 日常工作环境后，围绕 LibreOffice、Neovim 和终端 AI 工具 pi 搭起的一套工作台。它不是“一条命令告别 Windows”的教程，也不是一张装满软件图标的截图。比安装了什么更值得记下来的，是这些工具怎样接起来，以及它们在哪里接不上。

# 先把“完全迁移”说清楚

现在这套工作环境运行在 Ubuntu 26.04 上。开发、文件检索、Git、构建和调试的主线已经放进 Linux，而不是只在 Windows 里偶尔开一个 Linux 终端。

但“完全迁移”说的是**日常工作的重心**，不是宣称已经删除了磁盘上的所有 Windows 分区，更不是证明每一种 Windows 软件都有替代品。

同样，我说的“全终端化”，也不是不用浏览器、不看图片、不打开办公软件。更准确的说法是：**尽可能从终端进入任务，让命令、文件和结果能够连成一条可追踪的路径；确实需要图形界面时，就正常使用它。**

这两句话听起来不够激进，却能省去很多为了证明“纯粹”而制造的麻烦。

# LibreOffice：能打开，只是第一关

代码可以换编辑器，协作文档却不能要求所有人跟着换格式。讲义、报告和演示文稿仍然会以 DOCX、PPTX 的形式出现。迁移首先得接住这些真实任务。

LibreOffice 在这里负责文档和演示文稿的阅读、编辑与导出，但我不会把“支持这个扩展名”理解成“与 Microsoft Office 完全一致”。字体、公式、分页、动画和嵌入对象都可能成为差异来源。能读到文字，与适合交付，是两种不同的验收。

11 月 16 日就有一次很具体的提醒：一份 PPTX 打不开。

最初看上去像是办公软件出了问题，但排查时，其他演示文稿能够正常打开，问题收敛到了这份文件本身。最后定位到它内部文件索引的写法与 LibreOffice 的兼容问题；规范索引后，修复副本的 26 页都能读取，窗口也正常打开。原文件保留，文字、图片和视频资源没有改动。

这件事不能推出“以后所有 PPT 都没问题”，也不证明每一页的动画和排版已经与 PowerPoint 逐项一致。它说明的是另一个更实用的习惯：**先分清是程序普遍失效，还是某一份输入触发了问题；修复副本，不拿原件冒险。**

文档处理也有适合交给命令行的部分。比如下面是一个简化的 PDF 导出示例，需先准备好自己的 `report.docx`，导出后仍要打开检查：

```bash
mkdir -p export
libreoffice --headless --convert-to pdf \
  --outdir ./export ./report.docx
```

这只是命令用法，不是本文重新做过的一次格式兼容测试。导出命令退出，并不替代对分页、字体和公式的目视检查。需要共同编辑时按约定交源文件，需要固定阅读版时再附 PDF；PDF 也不能反过来代替可编辑原稿。

# Neovim：先接通反馈回路，再记快捷键

我的编辑环境是 Neovim 加 LazyVim，接入 C/C++、Python、Shell、Lua、JSON 和 Markdown 的相关工具。文件搜索、项目内检索、定义跳转、诊断、格式化和终端入口都围绕项目目录组织。

这套配置里有一个刻意保留的选择：**默认不在保存时自动格式化。** 需要时手动触发，避免刚接手一个项目，就因为保存文件产生一大块与任务无关的格式差异。

不过，编辑器能补全，不代表项目能编译；没有红色波浪线，也不代表程序正确。终端工作流真正重要的部分，是把编辑之后的反馈接回来。

以一个已配置好测试的 CMake 项目为例，可以把流程写成下面这样。它是通用示例，不是对任意工程都适用的安装脚本：

```bash
cmake -S . -B build -G Ninja \
  -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake --build build
ctest --test-dir build --output-on-failure
```

`compile_commands.json` 把编译参数提供给 clangd，让语言服务更接近真实构建环境；Debug 构建则为后面的 GDB 调试保留必要信息。工程本身的依赖、编译器和测试配置，仍然要另外准备。

还有一个看似基础、实际上必须分清的问题：**眼前是哪一种提示符？**

- 在 Shell 里输入 `cmake`、`git`、`python3`。
- 在 Neovim 普通模式里，用 `:w` 保存，按 `i` 进入输入模式。
- 进入 GDB 后，在它的提示符里输入断点、运行和查看变量的命令。

把几个窗口都放进终端，不会让它们变成同一种语言。先知道自己在和谁说话，比背下一整页快捷键更有用。

# 终端工作台不是一个软件

Neovim 不需要承担所有任务。我把其他事情分给更小的工具：

- **tmux** 管会话、窗口和分屏，让编辑、编译和 AI 对话可以并排放着。
- **Yazi** 管文件；配置过的 `y` 函数还能在退出后把 Shell 切到选中的目录。
- **ripgrep、fd、fzf、zoxide** 分别帮助搜索内容、查文件、模糊选择和跳到访问过的目录。
- **lazygit** 用文字界面查看暂存区、差异和提交，不要求每一步都靠手敲长命令。
- **btop** 看资源与进程；排错时再按需使用系统日志和其他命令。

它们的价值不是“比图形软件更有黑客感”，而是可以围绕同一个目录工作，不必不断重新告诉每个工具：项目在哪里，刚才改了什么。

我还把重复动作收成了几个自己的入口：

```bash
work .      # 创建或接回当前项目的 tmux 会话
v .         # 用 Neovim 打开项目
y           # 用 Yazi 浏览，退出后回到选中目录
lg          # 打开 lazygit
termhelp    # 查看自己的工作台速查表
```

这里的 `work`、`v`、`y`、`lg` 和 `termhelp` 是本机脚本、函数或别名，**不是装上 Linux 就有的标准命令**。对一个刚迁移的人，把这些区别写清楚，比展示一段无法直接复现的终端录像更有帮助。

tmux 也不是任务永生器。退出客户端后，只要服务器和相关进程仍在，会话就可以接回；注销、关机或重启则可能终止它们。该保存的文件、该落盘的任务状态，不能交给“窗口还在”这件事来保证。

# 一次图片预览，把边界暴露出来

我确实尝试过让 Neovim 读的不只是代码。

DOCX 可以借助 `nvim-docx` 转为 Markdown 内容视图，配合渲染插件看正文、标题和表格。快速读材料时很方便，但这不是 Word 页面预览，不会精确复现分页、页眉页脚和复杂版式。

而且它不是绝对只读：只打开阅读不会改写原文件，编辑后执行 `:w` 却可能写回 DOCX。重要文档应先留副本；要核对最终排版，仍然回到办公软件或导出的 PDF。

图片则暴露了终端模拟器之间的差别。Kitty 可以内嵌原图；我使用的 Ptyxis / VTE 环境不支持相同的图像显示路径。最后的处理不是继续把二进制当文本打开，也不是强行宣称“任何终端都能看图”，而是让 Neovim 调用系统图片查看器，自己留下不可编辑的提示缓冲区。

这一步用了图形界面，却让工作流更可靠。**从终端发起，与最终以文字界面呈现，是两回事。**

PDF 也有类似边界：`pdftotext` 适合提取有文字层的内容，不负责复原所有视觉布局；扫描件需要 OCR，公式和图表更不能只看提取出的文字就下结论。

# 把 AI 接进 pi，而不是反复搬运代码

终端工作台搭好后，AI 也不必一直待在另一个聊天网页里。

我使用 pi 作为终端里的 AI 编码助手。进入项目目录后启动它，让对话围绕实际文件、命令输出和修改差异展开；Neovim 留着编辑，旁边的终端可以构建测试，另一个窗口放 pi。

```bash
# 先在 Shell 中进入要处理的项目目录
pi
```

模型与访问凭据需要预先配置。pi 本身不是模型，也不是“装好就免费获得无限 AI”；它连接什么服务、发送什么上下文、如何计费，取决于实际配置。这里不公开个人接口、令牌或账号配置。

对学习任务，我更愿意把协作范围说得具体一些。下面是一种提示方式，不是某次对话的逐字摘录：

> 先读构建配置和失败日志，解释报错的原因。暂时不要修改代码。给我一个最小验证步骤，我自己在 Neovim 里改完，再检查结果。

也可以把任务限制为阅读差异、检查测试覆盖或整理文档。重点不是让助手替我完成一切，而是让它进入已有的反馈回路，而不是另外制造一份脱离项目的答案。

这里也有不能省略的安全边界：**能执行命令，不等于命令安全。** pi 不会因为运行在终端里，就自动替我隔离文件、隐藏密钥或阻止破坏性操作。第三方模型服务还可能接收到任务所需的代码与上下文，因此应限制工作目录、工具权限和可发送资料，敏感内容另行处理。

修改后仍然看 `git diff`，该跑的测试自己确认；涉及删除、安装、提交、推送或部署时明确范围。AI 的解释可以是线索，真正的验收仍然来自可检查的文件和执行结果。

顺便说一句，这些工具并不都专属于 Linux。Windows 同样可以有终端、Neovim 和 AI 助手。迁移的价值，不需要靠否认另一套系统的能力来成立。

# 装好了之后，还有哪些没测过？

装好一套工具以后，很容易把“程序启动了”当成结束。10 月 14 日的工作台记录里，我留下了更细的检查：编辑器行为 27 项、终端行为 13 项通过，实际走过语言服务、搜索、编译、测试和会话恢复等路径。这些数字的用途，是让我知道当时究竟检查了什么，不是给桌面打分。

同一份记录也留下了没检查完的事情：健康检查里仍有可选预览和运行时提示；剪贴板提供者可用，但没有覆盖当时的剪贴板做往返测试；也没有做重启验收。之后补上图片预览，并不意味着其他提示自然消失。

这些留白应该和成功记录一起保留。否则，几周后面对一次失败，很容易把“我记得装好了”误当成“这个路径确实测过”。

配置本身也需要维护：保留 Neovim 的插件锁文件，修改前备份相关配置，尽量一次改变一件事。若要把 dotfiles 放进公开仓库，先挑选并检查文件，而不是把整个配置目录连同凭据和私人路径一起上传。

# 迁移真正留下了什么

这套环境并没有让所有事情都变简单。办公格式要复核，终端能力有差异，插件会变化，AI 也会出错。终端化不是消灭这些问题，而是让更多问题有一个可以定位的入口。

现在，一项开发任务可以沿着同一条路径走下去：找到目录，读文件，编辑，构建，测试，看差异，记录结果。需要帮助时，pi 加进来；需要看排版时，LibreOffice 加进来。它们不必互相取代。

如果重新整理迁移顺序，我会先保住文档交付和基本开发，再接通检索、会话与版本管理，最后处理那些确实影响日常使用的小摩擦，而不是先追求一个看起来无所不能的桌面。

从 Windows 到 Linux，最后值得留下的不是一张“已经彻底迁移”的证明，而是一套下次遇到问题时仍然能接着用、也能逐步修好的工作方式。
